## Findings considered and rejected / deferred

- **Decompose `lib/editor-store/store.ts` (4,147 lines) into slices** (DEBT-01):
  high value but L-effort and MED-risk to undo/redo; defer until plan 004's
  characterization coverage exists. A safe first slice (export handlers) was
  already extracted to `components/editor/use-export-actions.ts`.
- **Canvas full-SVG rebuild via `innerHTML=''` + 19 store subscriptions**
  (PERF-01/03/04, D4): real, but rewriting the render path / splitting Canvas
  is high-regression-risk without visual coverage. Deferred; revisit after a
  Playwright visual baseline exists.
- **`structuredClone` on history snapshots** (PERF-05): cost is real only on
  very large projects; needs a profiler trace before committing to a
  copy-on-write rewrite. Deferred (needs evidence, MED confidence).
- **store.ts `editScope`/`currentIconId!` non-null assertions** (CORRECTNESS-01
  through -10): the audit itself confirmed these are guarded by optional
  chaining and "safe in practice." Code-clarity, not live bugs. The one
  worthwhile sub-item — making the temporal `resume()` idempotent against
  nested pause/resume — is low-impact (no caller nests today) and folded into
  the maintenance notes of any future store-slice plan. Not worth a standalone
  plan.
- **npm publish-proxy registry allowlist port confusion** (SECURITY-06): the
  current `new URL(registry).origin` + exact-match allowlist is already
  correct; the "fragile normalization" claim did not reproduce on inspection.
  Rejected.
- **GitHub sync file-path traversal** (SECURITY-08): MED confidence, downstream
  provider applies its own guards and the API is not a public attack surface
  (caller is the authenticated user's own session). Low leverage; fold the
  one-line `..`/absolute-path reject into plan 002 only if cheap.

## Direction options (for the maintainer — not scheduled as build plans)

These are grounded forward-looking options, presented for a human to weigh, not
ranked against the bug/debt plans above. Each would start as a design/spike,
not a build-everything plan.

1. **Lottie round-trip import** (DIRECTION-01): `lib/export/export-lottie.ts`
   is mature, but there is no Lottie *import* adapter — users can't re-open
   their own exports. An 80%-fidelity adapter (shapes, basic keyframes, fills)
   is M-effort; full fidelity (expressions) is L.
2. **Import-from-share round-trip** (DIRECTION-03): `/share` renders a
   read-only icon decoded from the URL fragment, but there is no
   "import this shared icon into my project" path. The decoder
   (`lib/platform/share-link.ts`) already produces a valid `Icon`; wiring it
   into the import dialog is S-effort.
3. **CLI transition authoring** (DIRECTION-02): `packages/hiero-cli` can
   scaffold/validate/build but not author transitions (its own README lists
   this). A CLI-native transition contract would unblock pure-headless
   workflows. Design spike first — validate the DX is even wanted vs. "use the
   web editor for transitions."
4. **Formalize the R7 headless export API** (DIRECTION-04):
   `docs_canonical/NEXT_PHASES.md` R7 wants server-side embedding; the export
   functions already run in Node but aren't a versioned public contract.
   Design spike: audit `lib/export/*` for browser-only deps, define a stable
   `@hiero/export-api` surface.
